# Supabase (Postgres) Migration — Design

**Date:** 2026-09-09
**Status:** Approved design, pending implementation plan
**Replaces:** MongoDB (`pymongo`) as the agent's persistence layer

---

## 1. Purpose and scope

Replace MongoDB with Supabase/Postgres as the single store for the `bbc` agent and web
app. `agent/store/db.py` is already a thin DAO (50 public functions) and the Mongo
surface is confined to three files, so the migration is a rewrite of the DAO plus a
schema, not a rewrite of the agent.

**In scope:** schema DDL, DAO rewrite against Supabase, config, test-harness swap, and
documentation.

**Out of scope:** any change to agent behaviour, reasoning, GraphRAG, the barbell
strategy, treasury semantics, or the Solana anchoring path. This migration must be
behaviour-preserving: the same 158 tests must pass, unchanged except where they assert
Mongo-specific mechanics.

---

## 2. Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Client library | `supabase-py` (PostgREST over HTTPS) | The only credential available is a publishable key. Direct `psycopg` needs the database password, which we do not have. |
| Credential | `SUPABASE_SERVICE_ROLE_KEY` **if set**, else the publishable key | Operator chose publishable-only. The fallback costs nothing and makes hardening a one-variable change rather than a refactor. See §6. |
| JSON columns | Postgres `text`, **never `jsonb`** | `db.py` stores JSON as verbatim strings so on-chain trace hashes stay byte-identical. `jsonb` normalises key order and whitespace, which would break `/verify/<id>` for every previously anchored trace. |
| Integer ids | `bigint generated by default as identity` | Replaces the `counters` collection and its `find_one_and_update` autoincrement emulation. |
| String ids | `text primary key` | `markets._id` is `"{venue}:{external_id}"`; `treasury._id` is the constant `"main"`. |
| Test harness | In-memory fake PostgREST client | See §5. Preserves all 158 tests without a live database. |
| Schema creation | Operator runs the generated SQL once in the Supabase SQL editor | DDL is impossible with a publishable key. |

### Non-goals

- No data migration from the existing MongoDB. The store is rebuilt empty and reseeded
  via `init-db`; historical paper trades are not carried over. **If existing history
  must be preserved, that is a separate export/import task.**
- No change to the `counters` semantics beyond replacing them with identity columns.

## 3. Schema

Sixteen tables, one per collection: `markets`, `decisions`, `positions`, `orders`,
`market_snapshots`, `metrics`, `graph_nodes`, `graph_edges`, `graph_runs`,
`onchain_anchors`, `trace_blobs`, `breaker_state`, `blocklist`, `llm_usage`,
`treasury`, `treasury_events`, `flywheel_events`.

Rules binding the DDL:

1. **Hash-critical columns are `text`:** `markets.raw`, `decisions.search_used`,
   `decisions.response_json`, `market_snapshots.raw`, `graph_runs.ontology_json`,
   `graph_runs.stats_json`, and the trace-blob payload. Never `jsonb`.
2. **Identity columns start above any existing max id.** If history is ever imported,
   sequences must be reset with `setval`, or new rows collide with old ones.
3. **Indexes mirror `init_db()`** exactly, including the UNIQUE index on
   `flywheel_events.position_id` (the flywheel's idempotency guarantee) and the unique
   `(market_id, as_of)` on `market_snapshots`.
4. **Timestamps stay `text`** holding ISO-8601 UTC strings, matching what the DAO
   writes and what `positions_today_pnl` pattern-matches on. Converting to
   `timestamptz` would change comparison semantics and is out of scope.
5. Nullable/`default` choices mirror the documents the DAO writes today.

The DDL ships as `agent/store/schema.sql` — restoring the file `CLAUDE.md` has always
claimed exists.

## 4. DAO rewrite

`agent/store/db.py` keeps **every public function signature and return shape**. Callers
across the agent, the API, and the treasury package are unchanged. Internals change:

- `connect()` yields a Supabase client rather than a `Database` handle. It remains a
  context manager so no call site changes.
- `_row()`/`_opt()` currently map Mongo's `_id` to `id`. Postgres columns are already
  named, so these become identity/no-op mappings but are retained so call sites and
  return shapes stay identical.
- `next_id()` is deleted; inserts return the generated id via PostgREST's
  representation response.
- Mongo query operators map to PostgREST filters: `$ne` → `.neq`, `$in` → `.in_`,
  `$regex` prefix → `.like`, `$set` → `.update`, upsert → `.upsert(on_conflict=...)`.
- `positions_today_pnl`'s `^today` regex becomes a `like` on the ISO date prefix.

### Transactional integrity (an improvement, not a port)

Under Mongo, `db.open_position` opened a **nested second connection** to write its
treasury event, so a crash between the position insert and the ledger event left the
book unreconstructible — the exact invariant the treasury sells. PostgREST does not
expose interactive transactions, so this migration does **not** silently claim to fix
it. The ordering (position first, ledger second) is preserved, and the gap is
documented in `CLAUDE.md` as a known limitation with the remedy noted: a Postgres
function (RPC) performing both writes atomically, once a secret key is available to
create one.

## 5. Testing

`tests/conftest.py` currently injects `mongomock`. There is no local Postgres available
(no `mongod`, no Docker daemon), and running 158 tests against the live Supabase project
would be slow, flaky, and would pollute real data.

Therefore: **an in-memory fake of the narrow PostgREST surface the DAO uses**
(`table().select().eq().order().limit().execute()`, `insert`, `update`, `upsert`,
`delete`), backed by dicts. It is test-only, lives in `tests/fakes/`, and implements
exactly the operations `db.py` calls — no more.

**This is the migration's main risk and it is stated plainly:** a fake can diverge from
real PostgREST. It is mitigated by a small integration smoke test, run manually against
the live project, that exercises one insert/select/update/delete round-trip per table
group and is skipped by default via an env flag.

---

## 6. Credentials and RLS

`agent/config.py` gains `supabase_url`, `supabase_publishable_key`, and
`supabase_service_role_key` (optional). The client prefers the service role key when
present.

**Stated plainly, per the operator's decision:** with only the publishable key, the
agent's writes require RLS disabled or policies permitting anonymous inserts. That makes
the trading ledger writable by anyone holding a key that ships in the browser bundle,
which contradicts the tamper-evident claim in `submission.md`. The generated SQL will
therefore include the permissive policies needed to work today, each with a comment
naming what it exposes, and a commented-out hardened policy set to switch to once a
service role key exists.

---

## 7. Verification

- All 158 existing tests pass against the fake, unchanged except where they assert
  Mongo mechanics.
- `python -m agent init-db` succeeds against the live project and seeds the treasury.
- One real cycle in `paper` mode writes a market, a decision, and a treasury event.
- `/api/treasury`, `/api/flywheel`, `/api/positions/settled` return correct payloads.
- A previously anchored trace still verifies at `/verify/<id>` — proving the `text`
  column choice preserved hash byte-identity.
